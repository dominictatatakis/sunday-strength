# Signing in with Google and Apple — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sign in with Apple and Google inside the iOS app, keyed on the
provider's stable subject rather than the email, with first-time sign-ins
asked the four training questions before any row is written.

**Architecture:** A stdlib `providers.py` (ported from Kith, with its nonce
bug fixed) turns a provider credential into a `ProviderIdentity`. One
`_resolve_identity` in `app.py` decides which subscriber that is, and every
Google and Apple path — the existing website routes included — goes through
it. The phone gets a long-lived signed refresh token, because a provider
account has no password to replay when the 30-day cookie expires.

**Tech Stack:** FastAPI, SQLite/Postgres via `db.py`, stdlib `unittest`;
SwiftUI, AuthenticationServices, CryptoKit, XcodeGen.

**Spec:** `docs/superpowers/specs/2026-09-23-sso-design.md`

## Global Constraints

- No new dependencies on either side. RS256 is verified with hashlib, as in Kith.
- `subject_id`, never email, identifies a provider account.
- Never link on an unverified email. Never auto-link a relay address
  (`@privaterelay.appleid.com`).
- No preferences → no subscriber row. Nothing half-made.
- A provider button appears only when the server advertises it.
- British English in user-facing copy.
- `/subscribe` must still refuse an email that already has an account.
- Plans stay deterministic; nothing here touches `engine.py`.

## Departures from the spec, decided here

- **Google on the phone uses Kith's pattern, not PKCE.** The app opens
  `/login/google?app=1` in `ASWebAuthenticationSession`; the server does the
  exchange at its existing `/auth/google` callback and sends the phone back
  through `sundaystrength://auth` with a one-minute signed handoff (or a
  signed pending identity when onboarding is needed). This needs no second
  Google client and no change to the Google console.
- **The phone gets a refresh token.** The app keeps the password in the
  Keychain to sign in again silently; a provider account has none. Provider
  sign-in returns `{"refresh": ...}` — `db.sign_data({"refresh": id})`, valid
  a year — and `POST /api/v1/auth/refresh` swaps it for a fresh `ss_session`.
- **New accounts from the app only while payments are off (`DEV_MODE`).**
  With billing on, the app cannot take payment (App Store 3.1.1), so the API
  answers `403 no_account` for someone new and the app says so, with no link.
- **Sign in with Apple on the website is out of scope.** It needs a Services
  ID created in the developer portal; `aud` checking already accepts one via
  `APPLE_SERVICES_ID` so it can be added later without touching verification.

## Review Focus

- A taken or missing email on a new account: the subscriber row needs a
  unique, mailable address, since the weekly plan is emailed there. Refuse
  (`409 email_in_use`) rather than invent one. A relay address is allowed as
  a new account's email — it is unique and mailable once the sending domain
  is registered with Apple — it is only never used to *link*.
- Apple's `email_verified` arrives as the string `"false"`: must read false.
- A refresh token must not be mintable from any other signed blob (OAuth
  state, handoff, pending): check the `refresh` key specifically.
- A handoff is single-purpose and expires in 60 seconds.
- The existing web signup through Google must keep carrying preferences and
  still go through `_finish_signup` (Stripe when billing is on).

### Task 3: one place that decides who an identity is

**Files:** Modify `app.py`; Test `tests/test_sso.py`

**Produces:** `_resolve_identity(conn, ident, prefs: dict|None) -> (Row|None, str|None)`,
problems `needs_onboarding`, `no_account`, `email_in_use`.

Order: identity row → verified, non-relay email held by a subscriber (write
the identity) → no prefs: `needs_onboarding` → payments on and not the web:
`no_account` → email missing or taken:
`email_in_use` → create subscriber with prefs, add identity.

- [ ] Tests: unverified email neither links nor creates; relay address does
  not link to an existing subscriber; no prefs writes nothing; second sign-in
  does not add a second identity; an existing password account links on first
  Google sign-in and keeps its completions.
- [ ] Rewrite `/auth/google` to use `providers.verify_google` (id_token `sub`)
  and `_resolve_identity`; web signup still passes prefs from state and ends in
  `_finish_signup`. Plain web login for someone new still returns `?sso=failed`.
- [ ] Green; commit.

### Task 4: the phone's endpoints

**Files:** Modify `app.py`; Test `tests/test_sso.py`

**Produces:** `GET /api/v1/auth/providers -> {"google": bool, "apple": bool}`;
`POST /api/v1/auth/apple {identity_token, nonce, name?, prefs?}`;
`POST /api/v1/auth/google {handoff} | {pending, prefs}`;
`POST /api/v1/auth/refresh {refresh}`. Success: `200 {"refresh": str}` and
the `ss_session` cookie. Errors: `401 unauthenticated`, `409
needs_onboarding` (with `pending` for Google), `403 no_account`, `409
email_in_use`, `404` when the provider is off. `/login/google?app=1` carries
`app` in signed state; the callback redirects to
`sundaystrength://auth?handoff=…` or `…?needs_onboarding=1&pending=…` or
`…?error=1`.

- [ ] Tests: providers endpoint reflects flags; Apple happy path returns a
  refresh token and cookie; bad prefs are 400; handoff older than 60 s and
  forged handoff/pending/refresh are 401; an OAuth state is not accepted as a
  refresh token; the app callback never puts a session token in the URL.
- [ ] Implement; rate-limit all four with the existing `ratelimit.hit`.
- [ ] Green; commit.
